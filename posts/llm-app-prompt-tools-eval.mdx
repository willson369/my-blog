## 背景

我做过几次“看起来很 AI”的小项目：文档问答、代码助手、本地知识库检索。早期我把时间花在挑模型上，后来发现：**大多数体验问题，不在模型榜单，而在系统边界。**

这篇文章不讲空泛概念，只讲我反复碰到、并且后来基本能稳定规避的三类问题。

## 问题一：把聊天框当成产品

最早的形态通常是：

```text
用户输入 → 拼一个超长 prompt → 等模型回答 → 直接展示
```

它能 demo，但很难变好。因为你没有：

- 明确的任务类型（问答 / 改写 / 抽取 / 执行）
- 失败时的降级策略
- 可观察的中间状态

我现在会先问自己：

> 如果模型完全不可用，这个产品还剩下什么价值？

如果答案是“什么都没有”，说明你还没做出产品，只是包了一层 API。

更好的切法是：先定义工作流，再决定哪里需要模型。

例如文档助手：

1. 检索候选片段（确定性）
2. 让模型基于片段作答（生成）
3. 强制引用或展示来源（可验证）
4. 无结果时明确说“没找到”，而不是编造

## 问题二：工具调用缺少契约

Tool Calling 很好用，但一旦工具定义随意，系统会迅速变脆。

我踩过的坑：

- 工具名语义不清：`doStuff`、`handle` 这种名字模型会乱猜
- 参数可选得太多：模型倾向于省略关键字段
- 错误返回不结构化：模型无法判断是重试、换工具，还是直接告诉用户失败

一个更稳的约定：

```ts
type ToolResult =
  | { ok: true; data: unknown }
  | { ok: false; code: string; message: string; retryable: boolean };
```

并且：

- 每个工具只做一件事
- 写操作默认串行
- 读操作才考虑并行
- 所有副作用都要可追踪

这和传统后端设计几乎同构。AI 并没有取消工程纪律，它只是把纪律的收益放大了。

## 问题三：没有评测，就只能靠“感觉”

“我试了三个问题，回答挺好”——这是最危险的通过标准。

哪怕是个人项目，我也建议养一个最小评测集：

| 用例 | 期望 |
| --- | --- |
| 文档里存在的事实问答 | 答对且带来源 |
| 文档里不存在的问题 | 明确拒绝或说未知 |
| 带歧义的问题 | 先澄清，不直接赌一个答案 |
| 工具失败场景 | 给出可读错误，不胡编成功 |

数量不必多，20 条就很有用。关键是**可重复**。你改了 prompt、换了检索阈值、调了温度，都应该能回放这 20 条，看回归了什么。

对学生来说，这反而可能是加分项：你不只会调模型，还会用工程方法约束模型。

## 我现在的默认架构（精简版）

```text
User Intent
  → Router（规则 + 轻量分类）
  → Retriever / Tools
  → Generator（带严格系统提示）
  → Validator（格式 / 引用 / 安全）
  → UI
```

注意中间有 Validator。很多“AI 胡说八道”在生成后就能拦住一半，前提是你愿意多写 30 行检查逻辑。

## 真实感受

做 LLM 应用最反直觉的一点是：

> 你花在“防止模型犯错”上的时间，常常比“让模型更聪明”更多。

这不丢人。传统软件本来就这样——校验、监控、回滚、降级，从来都是主体，不是边角。

如果你也在做 AI 功能，建议少问“用哪个最强模型”，多问：

1. 任务有没有边界
2. 工具有没有契约
3. 结果能不能评测

这三问过关了，模型换来换去都不可怕；这三问不过关，换再新的模型也只是换一种方式翻车。
