共享算力平台看起来像“把 GPU / CPU 租出去”，真正难的是 **同一设备的同一时间片，在多租户、多节点、高并发下只能成交一次**，并且到期后账单和设备状态必须自动对齐。

独立站点：[算力分时调度](https://compute-lease.vercel.app) · 源码 [willson369/compute-lease](https://github.com/willson369/compute-lease)。内核集中在一个 `lease-engine` 文件里：Redis `SET NX` 锁、`ZSET` 延迟队列、`INCR` 滑动窗口、pipeline 缓存，不拆一堆小文件、不加会撑爆 node_modules 的客户端库。

接上 `UPSTASH_REDIS_REST_URL` 后走无连接 HTTP Redis，适合 Serverless 上万人同时打接口。

## 1. 市场调研：B2B2C 共享经济的调度难点

B2B2C 意味着三层角色同时在线：

- **B 端资源方**：机房 / 工作室上架设备，要看到真实可租时段
- **B 端运营方**：平台做撮合、计费、风控
- **C 端租户**：刷新排期、抢热点时段，失败要立刻知道

共享单车抢的是“现在这一辆”。共享算力抢的是 **未来某个时间片**。于是会出现三个结构性难点：

1. **时间片冲突**：同一 slot 被多个租户同时点下单，库存不能超卖
2. **状态流转复杂**：`可租 → 锁定 → 已租 → 到期重置`，任何一步超时都会把设备和账单打歪
3. **读多写少但写极热**：排期查询是高频读，抢占是尖峰写。缓存要快，又不能把“已租”继续展示成“可租”

核心矛盾不是流量大小，而是 **读要近实时，写要强一致**。

## 2. 需求分析：三条必须闭环的业务链

| 能力 | 用户要什么 | 系统必须保证 |
| --- | --- | --- |
| 设备排期查询 | 打开日历立刻看到可租 slot | 热点短缓存；成交后秒级失效 |
| 抢占租赁 | 先到先得，失败可重试别的时段 | 跨节点互斥 + 落库防超卖 |
| 自动计费 / 重置 | 到期自动扣费，设备回到可租 | 异步触发，主下单链路不阻塞；消息可重放但不重复扣 |

周边能力（鉴权、发票、对账、监控）都服务这三条链。没有这三条，平台只是设备目录。

## 3. 技术选型：复杂缓存 + 并发冲突控制

选型原则：**查询走多级缓存，抢占走锁，正确性交给数据库，到期走消息。**

| 问题 | 选型 | 为什么 |
| --- | --- | --- |
| 排期热点读 | 本地 Caffeine + Redis | 进程内命中最低延迟；Redis 负责多节点共享与主动失效 |
| 跨节点抢占 | Redisson 分布式锁 | 同一 `lease:{device}:{slot}` 互斥，挡住惊群 |
| 落库扣减 | MySQL `version` 乐观锁 | 锁过期或绕过锁时，CAS 仍保证只成交一次 |
| 到期扣费 / 重置 | RabbitMQ 延迟队列 | 下单只投递到期消息，主流程不等待时钟 |

补充约束：

- 热点 slot 缓存 TTL 必须短（秒级），成交后双删：先清本地，再删 Redis
- 分布式锁只覆盖“读库存 → CAS 更新”的短临界区，不锁整个 HTTP 请求
- 乐观锁是正确性底线，分布式锁是性能与体验优化；两者不是二选一

## 4. 方案设计：主链路怎么串

```text
查询：Local Caffeine → Redis → MySQL → 回填短 TTL 缓存
抢占：Redisson tryLock(slot) → 读行 → UPDATE ... WHERE version=? AND status='AVAILABLE'
     → 成功则投递延迟消息 → 解锁 → 失效缓存
到期：延迟消息到达 → 扣费 + 设备重置（version 再 +1）→ 失败进重试，成功靠 version 幂等
```

抢占 SQL 只认这一句：

```sql
UPDATE time_slot
SET status = 'LEASED', tenant_id = ?, version = version + 1
WHERE slot_id = ? AND status = 'AVAILABLE' AND version = ?;
```

`affected_rows = 1` 才算抢到。其余请求要么锁等待失败，要么看到 `LEASED` 后直接返回已售。

到期消费同一套 version：只处理 `status='LEASED' AND version=下单成功时的新版本`。重复投递直接跳过，避免二次扣费。

## 5. 度量与容错（按主流云厂商拍板）

不再把这两件事留空：

1. **算力度量**：跟 RunPod / Vast / 云 GPU 一样用 **SKU + 卡时**。`CU = vCPU + GPU 权重`（T4=16 / 4090=32 / A100=56），用户看到的是型号和时价，不把 TFLOPS 暴露成计价单位。
2. **网络容错**：租约带 `leaseUntil`。节点失联后，**读路径懒过期 + 到期扫单** 都会把 slot 收回。脑裂时 **version CAS 是唯一真相**；锁只挡惊群，过期或绕过锁也不能超卖。不做跨机房任务迁移。

## 6. 验证

进程级仿真在 `scripts/simulate-lease-scheduler.js`。在线调度台是独立站点，不走博客域名。

```bash
pnpm simulate:lease
```

连续多轮稳定：

- **160 个并发抢占每次只成交 1 次**
- 锁 TTL 缩到 8ms，乐观锁仍只让 1 个 CAS 成功
- 延迟消息可重放，第一次扣费重置，后续 `IDEMPOTENT_SKIP`；误差约 3–4ms

独立站点可现场点「160 并发抢同一 slot」，再等 12 秒看到期入账。
