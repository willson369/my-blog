## 写在前面

过去一年，我写代码的方式变了。

不是“不会写了，全靠模型”，而是：**判断力仍然在自己手里，执行被大幅加速**。作为还在学校的开发者，这件事对我很关键——时间有限，试错成本又高。AI Coding Agent 最有价值的地方，不是替你交作业，而是把“查文档、改样板、做回归”这些耗时步骤压缩掉，让你把精力留给设计和验证。

这篇文章记录我目前比较稳定的一套工作流，以及踩过的坑。

## 我实际在用的工作流

### 1. 先写清“完成定义”，再让 Agent 动手

很多失败不是模型笨，是任务描述太糊。

我现在会先强制自己写四行：

1. **目标**：这轮结束时用户能看到什么
2. **约束**：不能改哪些文件 / 不能引入什么依赖
3. **验收**：怎么证明做对了（命令、页面、边界 case）
4. **回退**：如果失败，最小可回退点是什么

没有这四行，Agent 很容易“看起来很努力，结果不可用”。

### 2. 小步提交，而不是一次生成整站

我更喜欢这种节奏：

```text
理解现状 → 提出最小改动 → 实现 → 跑通 → 再扩一步
```

这和传统工程里的增量交付是一回事。差别只是：中间很多机械步骤可以交给 Agent。

如果你让它一次“重构整个模块并顺便加新功能”，成功率会直线下降。不是不能做大任务，而是**大任务必须被拆成可验证的小闭环**。

### 3. 把 Agent 的输出当 PR，不当真理

我审查 AI 代码时，优先看这几类问题：

- 有没有静默吞错（`try/catch` 空处理、默认值掩盖真实失败）
- 有没有改到不该改的公共状态（尤其是全局数组原地 `sort`）
- 有没有“为了通过编译”引入的临时类型逃逸
- 有没有把示例代码的品牌、域名、备案信息一起带进来

最后一条听起来像笑话，但模板站和开源脚手架里特别常见。

## 一个我反复验证有效的提示结构

```md
上下文：这是一个 Next.js App Router + Contentlayer 的静态博客。
目标：修复文章上下篇翻页索引错乱，确保列表展示全部博客文章。
约束：
- 不要迁移框架
- 不要改视觉大改版
- 不要引入新依赖
验收：
1. /posts 能看到全部博客文章数量
2. 打开任意文章，上一篇/下一篇按日期相邻
3. about 不出现在博客时间线里
```

越具体，返工越少。Agent 强不强，很大程度取决于你能不能把问题说成“可测试的工程任务”。

## AI 很擅长 / 仍然不擅长

**擅长：**

- 在陌生代码里快速定位可疑点
- 补测试脚手架、改文案、对齐类型
- 把重复劳动变成可脚本化步骤

**不擅长（至少目前）：**

- 替你承担产品决策
- 在信息不全时承认“我不确定”
- 长期维护一个复杂系统的架构一致性

所以我给自己定了条原则：

> **模型负责加速，人负责负责。**

出了线上问题，不能说“是 AI 写的”。能合并进主分支的代码，就是你的代码。

## 对学生开发者意味着什么

我还没毕业，简历上很难堆很多“负责过千万 DAU”的故事。但 AI 开发经验可以很具体：

- 你会不会把模糊需求拆成可执行任务
- 你会不会设计验收，而不是只看“跑起来了”
- 你能不能在 Agent 给出漂亮答案时，仍然做对抗性审查

这些能力，招聘方其实很容易在对话里测出来。

## 小结

AI Coding 不是魔法，是一种新的协作接口。

如果你只是把 Chat 窗口当成更快的 Stack Overflow，收益有限；如果你把它嵌进“拆解 → 实现 → 验证 → 复盘”的闭环，它会明显改变你的学习曲线。
